## Executive Summary

This report captures the current allocation and throughput profile of **Incursa.Quic**, a fully managed QUIC transport implementation, and compares it against **System.Net.Quic** (a managed wrapper over native MsQuic).

**Key findings from 2,000-iteration harness (pass 2):**

- **Incursa.Quic** managed allocation: **325 KB/op**
- **System.Net.Quic** managed allocation: **91 KB/op**
- **Incursa.Quic** throughput: **24.7 ms/op**
- **System.Net.Quic** throughput: **25.1 ms/op**
- **Managed allocation gap**: **3.6x** (Incursa higher in managed, System.Net.Quic higher in native)

**Critical context**: System.Net.Quic reports lower managed allocation because most QUIC/TLS work is delegated to native MsQuic. In this churn scenario the native path establishes a **~2.5 MB/op private-byte high-water mark**, while Incursa.Quic exposes more allocation to the managed GC but returns to a flat process-memory baseline after cleanup. Direct comparison of managed allocation alone between the two implementations is misleading.

**P4 optimization impact**: The P4 lazy server key generation reduced managed allocation from ~922 KB/op to ~325 KB/op (65% reduction). The server key schedule constructor dropped from ~596 KB/op to ~344 B/op (99.94% reduction), while maintaining the invariant that ECDHE/X25519 private keys are never reused across connections.

**Current status**: All metrics are within regression budgets. The remaining allocation is primarily runtime packet-processing infrastructure, not TLS micro-allocations.

## Managed Allocation Analysis

Incursa.Quic is a fully managed QUIC implementation, meaning all QUIC transport and TLS 1.3 handshake state, including cryptographic operations, packet buffers, and connection runtime objects, is allocated on the managed heap. The ~325 KB/op managed allocation reflects the total cost of establishing and tearing down one QUIC connection through the public API.

This allocation is spread across hundreds of small allocations: connection runtime construction, stream state objects, TLS handshake body builders, HKDF intermediates, crypto contexts, and packet scratch buffers. No single source dominates after the P4 server key schedule optimization.

The managed allocation is fully reclaimed by the GC after each operation. Pass 2 working set and private bytes deltas are near zero, confirming there is no managed memory leak.

---

## Native / Private Memory Analysis

### Incursa.Quic

Incursa.Quic uses no native QUIC library. All QUIC work happens in managed code. The private bytes delta per operation is ~2.5 KB/op in pass 2, which represents residual process-level allocation (primarily .NET runtime internals, socket handles, and certificate store access). This is effectively flat after cleanup.

### System.Net.Quic

System.Net.Quic delegates QUIC work to native MsQuic via P/Invoke calls. MsQuic allocates native memory for connection state, TLS context, congestion control, flow control, stream buffers, and packet I/O. These allocations are invisible to `GC.GetTotalAllocatedBytes`.

The plateau test shows that after `CloseAsync` and `DisposeAsync`, native MsQuic retains ~2.5 MB per connection in the process private bytes. This is consistent with a native allocator that caches allocations for reuse rather than returning memory to the OS immediately. Batch 2 shows slightly lower retention than batch 1, confirming this is high-water behavior rather than an unbounded accumulation.

### Plateau Test Detail

The `--leak` test creates N connections, captures memory at live state, then disposes all connections, triggers GC, waits 10 seconds, and captures again. Two batches are run to distinguish transient warmup effects from sustained retention:

- **Live delta**: Memory growth from baseline to all-connections-live state
- **After close+dispose**: Memory remaining after disposal and 10-second settle period
- **Retained from baseline**: The prior-baseline memory that was not released

System.Net.Quic native allocator behavior is a known characteristic of the MsQuic library and is not classified as a functional deficiency for this comparison.

## P4 Optimization Result

The P4 optimization changed `QuicTlsKeySchedule` so that server-side key generation is lazy and selected-group based. Previously, the server constructor eagerly generated a complete ECDHE key pair (including secret agreement, key derivation, and handshake traffic secret computation), costing ~596 KB/op. With P4, the server key schedule defers key generation until a compatible group is selected during the handshake.

**Security invariant preserved**: ECDHE/X25519 private keys are never reused across connections. Each connection generates a fresh key pair.

| Metric | Before P4 (historical) | After P4 (measured) | Change |
|---|---|---|---|
| Server key schedule constructor | 596,611 B/op | 344 B/op | **-99.94%** |
| Full server runtime constructor | 611,371 B/op | ~15,100 B/op | **-97.5%** |
| Connect+accept phase | 851,807 B/op | ~256,737 B/op | **-69.9%** |
| Total managed allocation (harness pass 2) | ~922,000 B/op | ~325,098 B/op | **-64.7%** |
| Throughput | ~29 ms/op | ~24.7 ms/op | **+14.8% improvement** |

*Note: "Before P4" values are historical baseline measurements documented in `PERFORMANCE-ANALYSIS.md` and the allocation investigation. They are not re-measured in this report. The "After P4" values are from this fresh run.*

The P4 optimization eliminated the single largest allocation hotspot in the codebase. The remaining ~325 KB/op managed allocation is distributed across hundreds of structurally necessary allocations in the connection runtime, handshake pipeline, and packet processing infrastructure.

## Limitations

- **Machine-specific results**: Measurements were taken on a single Windows workstation (AMD Ryzen 9 3950X, 96 GB RAM). Results may vary on different hardware, OS versions, or under memory pressure.
- **Loopback-only**: The harness uses loopback connections. Real network conditions (latency, packet loss, congestion) would produce different allocation profiles and throughput numbers.
- **Churn scenario**: The harness measures rapid connect/dispose cycles. This represents connection-churn workloads but does not represent steady-state streaming or long-lived connection scenarios.
- **System.Net.Quic private-byte high-water**: The ~2.5 MB/op retained private bytes is native allocator behavior, not automatically a leak. This is a known characteristic of MsQuic's internal memory management and does not indicate a functional defect.
- **Managed allocation/op metric**: `GC.GetTotalAllocatedBytes` measures GC-visible managed heap allocation only. It excludes native allocations, thread stacks, JIT code, and GC internal structures. It is not a total-memory or total-cost metric.
- **Isolated sub-operation measurements**: `--profile-handshake` measures sub-operations in isolation. Actual handshake costs include async message exchange, ordering dependencies, and shared-state effects not captured in isolation.
- **Throughput context**: Loopback throughput numbers (24-25 ms/op) reflect connection establishment and teardown overhead, not application data throughput. Throughput should be validated with real ProtocolLab scenarios or external load drivers before making broad claims.
- **Test suite**: The test suite was not executed as part of this evidence run due to a pre-existing build issue. Functional correctness should be validated separately.
- **Iteration count**: The harness used 2,000 iterations rather than the standard 10,000 to keep measurement time practical. Pass-2 metrics at 2,000 iterations are stable and representative, but higher counts would provide narrower confidence intervals.

## Next Work

1. **Packet-pipeline profiling**: The remaining ~222 KB/op in "remaining handshake processing" is the largest unattributed bucket. Profiling the full handshake packet pipeline (message assembly, CRYPTO frame encoding, packet serialization, transmit queue management) is the most promising avenue for further allocation reduction.

2. **Stream-level allocation**: Profile per-stream allocations (TaskCompletionSource, SemaphoreSlim, StreamState) under multi-stream workloads. The current harness measures single-stream connection establishment; real workloads with concurrent streams may reveal different hotspots.

3. **Completion source pooling**: Evaluate cross-connection pooling of `IValueTaskSource` objects rather than the current per-connection `ConcurrentQueue` pools. This could reduce per-connection structural allocation, especially for server scenarios with many concurrent connections.

4. **Steady-state benchmarking**: Extend measurement to include steady-state data transfer scenarios (stream reads/writes, ACK processing, congestion control behavior) to complement the current churn-focused measurements.

5. **Linux cross-platform baseline**: Run the same harness on Linux to establish cross-platform allocation and throughput baselines. .NET GC behavior and OS memory management differ between platforms.

6. **Fuzzing evidence**: Add fuzzing coverage for wire-facing parsers, serializers, decoders, and encoders as required by the proof burden in `AGENTS.md`.

7. **ProtocolLab validation**: Validate throughput claims with real ProtocolLab scenarios or external load drivers (`h2load`, HTTP/3 endpoints) before making broad performance claims.

8. **Fix test project build**: Resolve the missing `Incursa.Quic.Dns` project reference so the full test suite can run as part of the evidence pipeline.
